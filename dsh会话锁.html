dsh 的会话锁：我查到的（2026-11-14 00:45）

给自己以后看。事实来源都标了，不靠记忆。

一句结论

一个会话同时只能有一个写者，锁是内核级的 flock(2)，谁打开写句柄谁就拿着，直到那个句柄关掉。 没有"借用"，没有"只读写"。

事实

事项事实来源
锁文件<session 目录>/session.lockdsh-session-persistence-jsonl
机制POSIX flock(2)，非阻塞；抢不到抛 SessionAlreadyOwnedError同上
释放时机持有者进程退出 / 句柄关闭（崩溃也会放）注释原文
谁拿着本机实测：dsh web 进程（PID 79006）长期持有lsof//proc/*/fd
释放接口没找到。没有 HTTP/RPC 能叫 web 主动放手未找到，存疑

这意味着什么

网页版一加载这个会话  →  拿锁  →  直到进程死才放
QQ/中转台想写        →  SessionAlreadyOwnedError  →  只能等或落盘

关标签页没用（进程还在），切新会话也没用（实测仍被占）。

试过的、不行或危险的

  • ❌ 让网关多等（改成 18 次 × 15 秒）：只是晚点失败
  • ❌ 消息落盘 + 自动补答：能存住，但补答同样撞锁
  • ⚠️ "网页没人连着就重启 web 放锁"：能通，但证明不了空闲——网络等待时日志 mtime 不变、网页轮次跑在常驻进程里没有子进程、检查完还可能来新请求。已停用。

还值得查的方向

1. Host 侧有没有权威的"在途轮次/工具执行中"状态（RPC 或内部注册表），能不能查询

2. 有没有协调式的"停止接单 → 等在途完成 → 释放所有权"

3. 能不能让 web 端在真正空闲时主动 close 写句柄（改持久化层或 session-controller）

4. 实在不行就接受：同一时刻只有一个入口是"活的"，其余排队落盘，靠人工切换

记住的教训

先找根因再修。这一晚前面两小时都在给一个根本进不了门的人排队。

追查结果：Host 侧没有权威的「忙闲」接口（01:06）

  • activeTurn / inFlight 这些字段只出现在客户端 UI 里（dsh-client-ui-chat、-trajectory），是从事件流推出来的，不是 host 的权威状态
  • 服务端没找到「当前会话是否在跑一轮」的查询入口
  • 所以「按空闲自动让位」这条路没有可靠依据，按 GPT 姐姐的意见：不做自动重启，只保留队列 + 人工让位

现状（稳定态）

  • 自动让位：已停用
  • 消息队列：保留，落盘、可见、可手动补答
  • 需要 QQ 中转进来时：人工让位（关掉网页版 / 或我手动重启一次 web）

这条线暂时到此，等有别的思路再继续。
